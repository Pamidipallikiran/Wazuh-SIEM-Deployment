# SOC Investigation Playbooks

Triage guidance for the alerts raised by this lab's custom detections. Each playbook
follows the same shape: understand the alert, scope it, decide, respond, record.

Field names below are as shown in the Wazuh Dashboard (Threat Hunting / Discover).
Suricata event fields appear under `data.*`.

## Common triage steps

1. **Read the alert.** Note `rule.id`, `rule.level`, `agent.name`, `data.src_ip`, `data.dest_ip`,
   `data.alert.signature`, and the timestamp.
2. **Identify the source.** Is `data.src_ip` a known asset (manager, admin workstation, scanner,
   monitoring host) or unknown? Check your asset list or DHCP leases.
3. **Scope.** Search the same source for the last 24 h across all rules:

   ```text
   data.src_ip: "<source>"
   ```

   Then search the same destination for other sources. A single source hitting many destinations
   is reconnaissance; many sources hitting one destination is a distributed attempt or an outage.
4. **Correlate with endpoint telemetry.** On the destination agent, look for authentication events
   (`rule.groups: authentication_failed` or `authentication_success`) in the same window.
5. **Decide:** benign / expected, suspicious (monitor), or incident (contain).
6. **Record** the outcome using the template at the end of this document.

## Playbook: ICMP Echo Request (rule 910009) and aggregation (rule 910010)

**Meaning.** Someone sent a ping to a monitored host. Alone, this is usually benign (admin
connectivity check, monitoring). Repeated pings from one source can indicate a ping sweep.

**Investigate**

- Filter: `rule.id: (910009 OR 910010)`, group by `data.src_ip`.
- One source, one destination, a few packets: likely troubleshooting.
- One source, many destinations over a short period: ping sweep. Look for follow-on rules 910011 / 910012.

**Common false positives.** Monitoring systems, uptime checks, an admin running `ping`.
Rule 910010 can also fire when *different* hosts each ping once (it is not scoped per source;
see `detection/README.md`).

**Respond.** Benign: close with a note. Sweep from an unknown internal host: identify the host
owner, check the host for compromise. Sweep from outside: no action beyond monitoring unless
ICMP should be blocked at the perimeter.

## Playbook: TCP SYN scan (rule 910011) — MITRE T1046

**Meaning.** One source opened many new TCP connections to the monitored host in a few
seconds, consistent with port scanning.

**Investigate**

- Filter: `rule.id: 910011`; note `data.src_ip` and the time window.
- Is the source an authorized vulnerability scanner or inventory tool? If so, suppress or schedule it.
- On the target, list listening services and compare with what should be exposed:

  ```bash
  sudo ss -lntup
  ```

- Check for subsequent activity from the same source: SSH attempts (rule 910012), web requests,
  new authentication successes.

**Respond.** Authorized scanner: document and tune. Unknown internal source: isolate the host
and investigate it. External source against an exposed service: confirm the exposure is
intended; consider a firewall block and review the services that responded.

## Playbook: SSH connection burst (rule 910012) — MITRE T1110

**Meaning.** One source made five or more new connections to TCP/22 within a minute. This is a
*network-level indicator* of brute forcing; it does not prove any login failed.

**Investigate**

- Filter: `rule.id: 910012`, then on the destination agent check authentication outcomes in the same window:

  ```text
  agent.name: "<agent>" AND rule.groups: (authentication_failed OR authentication_success)
  ```

- On the host:

  ```bash
  sudo grep -E "Failed password|Accepted (password|publickey)" /var/log/auth.log | tail -50
  ```

- **Any `Accepted` entry from the same source after a run of failures is a priority escalation.**
- Check for new accounts, new `authorized_keys` entries, and unexpected sessions (`last`, `who`).

**Respond.** Failures only: block the source at the firewall, confirm password authentication is
disabled or rate limited (see `docs/hardening/hardening.md`). Success after failures: treat as
compromise — isolate the host, rotate credentials and keys, preserve logs, and investigate persistence.

## Playbook: ICMP flood (rule 910013) — MITRE T1498

**Meaning.** One source sent 20 or more Echo Requests within 5 seconds.

**Investigate**

- Filter: `rule.id: 910013`; check packet volume and duration in the Suricata events.
- Is the host responsive? Check CPU and network saturation on the target and the segment.
- A lab test generated by `scripts/generate-test-events.sh --test flood` is expected; confirm
  nobody was testing before escalating.

**Respond.** Rate-limit ICMP at the host or perimeter firewall, block the source if it is hostile,
and escalate if service availability is affected.
